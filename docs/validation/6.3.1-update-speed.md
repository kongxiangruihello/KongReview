# 6.3.1 更新时进度不再停在八成；编好的程序不再重编

2026-11-10。作者 11 月 10 日来信：“在进行到 81% 时，速度也很慢”。

## 查明原因

依据作者正式应用的更新日志（`~/Library/Caches/KongReview-updates/update.log`），看 11 月 4 日 6.2.2 → 6.3.0 那次更新：

| 时刻 | 事件 |
|---|---|
| 13:21:15 | 开始构建 |
| 13:21:15 | 测试跳过（“这份源码（树 67c8c38）已在本机用同一版 Swift 测过”），6.3 的改动生效 |
| 13:21:15—13:22:23 | 编译新版本：`Build complete! (67.84秒)` |
| 13:22:28 | 开始安装 |

**1. 编译段的大头停在 81%。** 编译输出的步数很快走到 `[9 / 10] KongReview-product`，之后编译 KongReview 本身是一整步整模块优化，约一分钟没有新的步数输出。6.3.0 的进度条按步数算，这时总进度为：

- 构建进度：编译段 0.55 + 0.38 × 0.9 ≈ 0.89
- 应用里显示：0.08 + 0.82 × 0.89 ≈ 0.81

所以停在 81% 约一分钟，与作者看到的一致。

**2. “编好的程序不再重编”原本对不上。** 11 月 4 日已在分支上写了“同一份源码编过就直接用编好的程序”（c6156df），以 git 树、Swift 版本和 `Package.resolved` 的指纹为键。但比对作者 Mac 上两个源码文件夹的 `Package.resolved`：

| 文件夹 | GRDB 版本 |
|---|---|
| 测试文件夹 `~/Documents/KongReview-测试版` | 7.11.1（b83108d） |
| 应用内更新的源码文件夹 `~/Developer/KongReview` | 7.12.0（92a554c） |

原因是 `Package.resolved` 在 `.gitignore` 里，每个文件夹各自解析 `from: "7.0.0"`。后果有两个：
- 键永远对不上，编好的程序不会被用上；
- 测试用的依赖版本与正式应用不同。6.3 的“测过就不再测”只认 git 树，测的是 7.11.1，装上去的却是 7.12.0。

## 实现范围

**进度按用时走**（c6156df）
- 编译新版本时每秒按已用时间推进一次进度，说明写“已用 34 秒（上次用了约 68 秒）”。
- 超过上次用时就停在该段的 97%，说明改为“比上次久一些，请稍候”。
- 每次编译完记下用时（`update.lastCompileSeconds`）；没有记录时按 70 秒估计。
- 测试跳过时重新分配各段比例，编译段从约 13% 起，不再一开始就过半。

**编好的程序不再重编**（c6156df）
- 同一份源码、同一版 Swift、同样的依赖，在本机编译过的，`build-app.sh` 直接用编好的程序，只重写 Info.plist、重新签名。
- 编好的程序存在 `~/Library/Caches/KongReview-updates/builds/`，留最近 3 份。

**依赖版本写进仓库**（75b9da8）
- 把作者正式应用所用的 `Package.resolved`（GRDB 7.12.0，原样从 `~/Developer/KongReview` 取来）提交进仓库，只在 `.gitignore` 里保留核心包的那一份（核心包没有外部依赖）。
- 测试文件夹第一次就改用 7.12.0：编译日志写着 “Working copy of GRDB.swift resolved at 7.12.0”。

**日志**
- `build-app.sh` 在源码有本地改动、因而不用“测过 / 编过”的记录时，把改动列进日志。

**测试脚本**（作者 Mac 上，不在仓库）
- 加第 7 步：照应用内更新的做法再跑一次 `Tools/build-app.sh --test`，检查测试与编译是否都跳过，并记用时。

## 说明

- 本文件提交后 git 树会变，所以合并前要在最终提交上再全量跑一次，把那份源码也测过、编过。那次的结果写在 PR 说明里，不改本文件（一改树又变了）。
- 6.3.0 → 6.3.1 这次更新，由正式应用里的 6.3.0 驱动。6.3.0 的进度条不认得“已在本机编译过”这一行，但取源码后构建只要几秒，一闪而过；“按用时走”的进度要从下一版起才看得到。
