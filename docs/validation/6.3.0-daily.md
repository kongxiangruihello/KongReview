### 更新更快

用作者正式应用的 `update.log` 看 12:15:49—12:17:31 那次更新（6.2.2）的耗时：

| 阶段 | 用时 |
|---|---|
| 编译测试 | 约 11 秒 |
| 核心包与应用测试 | 约 14 秒 |
| release 编译 | 69 秒 |
| 图标、签名 | 几秒 |
| 合计 | 约 1 分 42 秒 |

**改动**：
- 同一份源码在本机测过、全部通过的，`Tools/build-app.sh --test` 不再测一遍。判定依据是 git 树相同，且 Swift 版本相同。
- 测过的记录写在 `~/Library/Caches/KongReview-updates/tested-trees.txt`，由测试脚本与更新各自写入。
- GitHub 上合并 PR 产生的提交，树与测过的分支末端相同；前提是分支已含 main 的最新提交，本 PR 已先合并 main。
- 更新进度条认得“已测过”这一行，直接越过测试段（`BuildLogProgress`）。

**编译实验**：在作者 Mac 上，release 构建先做一次全量编译，再碰一下 `HelpView.swift` 重编一次，分别计时。

| 构建方式 | 全量 | 改一个文件后 | 结果 |
|---|---|---|---|
| 现行：`--arch arm64`，整模块优化 | 89 秒 | 57 秒 | 成功 |
| 不加 `--arch` | 91 秒 | 56 秒 | 成功 |
| `--arch arm64` 且关掉整模块优化 | — | — | 失败：这一版 SwiftPM 的新构建系统不接受 `-no-whole-module-optimization` |
| `--build-system native`，整模块优化 | 88 秒 | 56 秒 | 成功 |
| `--build-system native`，关掉整模块优化 | 69 秒 | 40 秒 | 成功 |

- 不用整模块优化，每次更新约再省 16 秒。
- 代价是要换构建系统，且跨文件优化少了；运行速度受多大影响没有测过。所以这一版不采用，release 编译照旧。
- 第一轮实验里，关掉整模块优化的两项曾记为 17 秒、5 秒，后查明是编译失败（退出码 1）用掉的时间，不作数。
